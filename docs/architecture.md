# 架构（现在长什么样）

这份文档写代码现在的样子。它不写代码应该长什么样，也不写当初为什么这么选——那两件事分别是
`evolution.md` 和 `decisions.md` 的事。

读完它，你应该能回答三个问题：一次请求从进来走到出去，中间经过谁；每个文件管什么、不管什么；
哪几处改动最容易把状态搞乱。字段级的细节以代码为准，这里只写形状。

## 三个概念，别混着用

Skill 是一份写好的专业能力：说明加脚本，可以反复用。Task 是一次具体的活儿，跑完就结束，
下回是新的一条。Sub Agent 是可选来干活的人，不建它也能干。

三者不重叠。Skill 属于谁都能用的公共资产，Task 属于这一轮，Sub Agent 只是执行方式的一种。

平台把 Sub Agent 的边界画在"参数已经齐了"之后：主 agent 先弄清用户要什么，才把活儿交下去。
这样上下文天然隔离。顺带的效果是"重复问用户""状态讲到一半丢了""提问混进正文"这三类问题
平台接得住——不是因为写得更小心，而是结构上看得见它们：待答有标识（`answer_to`）、状态落在
`Task` 上、正文不算交付。它们还会发生，只是不再从平台手里溜过去。

## 每个文件管什么

链路是一条直线：配置进来，模型调出去，产物落到盘上。中间这些文件按三层摆。

最底下一层不碰业务。`config.py` 找程序所在目录（打包后是 exe 目录）、找资源目录、读
`.env`（第一次用到配置时才读，见 `load_env`）、统一三路 UTF-8、给出模型。`llm.py` 只做一件事：`safe_structured()` 要结构化输出，
失败重试一次，再失败给一个保守默认值，它不知道谁在调它。`aio.py` 保证一个进程一个事件循环。
这三个谁在上面用都行，自己不知道调用方是谁。

中间一层是三个领域。`skills.py` 和 `skill_pack.py` 管"会什么"：前者是 `Skill` 对象（`name` /
`description` / `instructions` 三个字段）、来源接口 `SkillSource` 和清单排版，后者是它的磁盘
实现（把技能文件夹读成 `Skill`，列出、读取它自带的文件），自己不做语义判断。`artifacts.py`
管"交付了什么"：产物库接口 `ArtifactStore` 加内存实现，存、取、发 ID、按类型定扩展名，落地
那一刻就写盘，不管技能。内置那张技能表就是 `skills.py` 里的一份字面量，读走 `builtin_skills()`
（给副本，不给 dict）。

再往上是执行。`executor.py` 跑一次任务，接受执行器申报 `ask_user`，限制循环次数，它不持有
状态、不跨轮，也不直接问用户。`agent.py` 是主 agent，`delegate` 工具、委托单渲染、快照用户
原话、试答都在这里，它不解析也不抽取参数。`graph.py` 只把四个节点拼成图，不做业务判断。

`handoff/` 是一组交接点的词汇表和模板，一个交接点一个模块，自己不持有状态。`trace.py` 是
事件总线加全量日志，每个 super-step、每个流式片段都记，正文一律不截。`stream.py` 是它拆出来
的传输层。`recorder.py` 负责落盘，`session.py` 管会话标识，`__main__.py` 是最简 CLI，
带一个示例技能，只为了能跑起来。

`app/` 是验证用的 CLI，不是库本体：`runtime.py` 负责装配和记录，`chat.py` 是交互入口。
`build_cli.py` 把 `app/` 打成 exe，发给没装 Python 的人试。

宿主只从 `sxagent/__init__.py` 的 `__all__` 取东西：一个装配入口（`build`）、要给的配料
（技能来源、产物库、模型）、要读的词汇（`Task` / `Outcome` / 事件总线 / 会话）。唯一的
模块路径 import 是装配动作 `import sxagent.recorder`（import 即自注册，装上全量日志；
不 import 就没有日志文件，那是宿主的选择）。

## 依赖只能单向走

```
config ──► trace ──► (所有模块都在写日志)
  │
  ├─► llm ──► executor ──► agent ──► graph
  │              ▲            ▲          │
  ├─► skills ────┘            │          │
  ├─► skill_pack ─────────────┘          │
  └─► artifacts ─────────────────────────┘
```

有三条边界是踩过坑才画出来的。`executor` 和 `agent` 互相不 import，公共的 LLM 调用都放
`llm.py`，否则两者会绕成环。`skills` 和 `artifacts` 是两个领域，一个管"会什么"，一个管
"交付了什么"，它们的改动理由不同，不该粘在一起。两个领域对外都是接口：技能从哪来是
`skills.SkillSource`（实现在 `skill_pack.py`），产物放哪是 `artifacts.ArtifactStore`
（实现在同一个文件里），库自己的代码只认接口，宿主注入自己的实现。

## 三个对象，一条不变量

Skill 是静态的技能包，住在 `skills.py`，只有名字、说明、指令三个字段。Task 是一次具体的
业务工作，跨轮存活，住在图状态的 `tasks` 里，字段定义在 `handoff/briefing.py`。Artifact 是
运行期交付物，住在 `artifacts.py`。三个对象各有各的家，不互相包含。

不变量只有一条，但它是硬的：`SkillSource.read_file` 只认 `files()` 报出来的文件。路径
穿越、二进制、超大文件都由这一条挡住，不需要第二套路径检查。加一处新入口时，只要它还走
这两个方法，安全性就自动成立。

## 一次 `invoke` 的时序

四个节点串成直线，其中只有 agent 是模型在跑，其余三个都是纯代码。

```
用户 ─► ① feed ─► ② prepare ─► ③ agent ─► ④ finalize
```

1. `feed` 只做投递。用户这句答复只投给 `answer_to` 指向的那一条待答；没有这个标识就一条
   都不投。投递之后才渲染台账、注入 messages——顺序反了，台账里就看不见新状态。这一步会
   跑执行器，通常 60 到 120 秒。
2. `prepare` 把台账注入上下文。
3. `agent` 是主 agent 的子图，一个完整的 agent：自己的模型、自己的工具、自己的循环。
   有未答的提问时它不发言，因为那一刻是决策点，不是对话轮次。它有三条路可走：直接回答、
   调 `write_artifact` 交东西，或者调 `delegate` 派活儿。前两条都不建 Task。
   需要用户补信息或做选择时它还可以调 `ask_user`（auto / inline 档的工具表里有它）：
   调用后这一轮到此结束，问题由平台贴成卡片，答复就是用户的下一条消息——机制与执行器的
   待答统一、语义各自（见 `decisions.md`）。
4. 调 `delegate` 时执行的是平台代码，模型跳不过去。先校验：技能名不存在就拒绝，产物 ID
   不存在也拒绝，两种都不建 Task。然后 `run_task()` 在隔离的上下文里跑执行器。执行器
   只有两种表态：申报 `ask_user` 表示缺信息，交产物表示做完了（交付含两条路：工具闭包记的
   `write_artifact`，和程序侧交付——工具在结果消息上带 `delivered_artifacts` 字段，执行器读字段入账）。三态由结构决定，不是模型
   判的，所以可以穷举分派——`waiting_for_input` 交给主 agent 强制试答，答不上才登记待答；
   `completed` 就交付，带上产物 ID、路径和摘要；`incomplete` 记为 failed，交回主 agent。
5. `finalize` 只做一件事：如果还有待答，把执行器申报的原话无条件贴进回复。

## 状态机

```
delegate 建 Task → running ─┬─ completed（交了产物）
                            ├─ waiting_for_input（调了 ask_user）
                            └─ failed（没有出口：既没交产物也没申报要信息）
   另有 superseded：同 skill 的 failed 旧 Task 被重新委派时自动标记
```

四个名字最容易看错，分开写：

- `waiting_for_input` 不等于图失败，它是正常状态，说明执行器在等一个信息。
- `completed` 不等于任务完成，它只说明"交了产物"这个事实。够不够，由主 agent 判。
- `failed` 不等于模型报错，它的定义是"既没交产物也没申报要信息"（它自己停下来就推它接着
  干，没有轮次上限，跑多久由墙钟管）。
- 执行器"跑完了"不等于 Task 完成。所以平台对外只报结构事实，不替谁下结论。

## 交接（这套系统的行为几乎都由它决定）

执行器是用完即弃的，它看到的所有东西都必须由平台重新交给它。三条规矩：

1. 用户原话由平台原样搬，不许模型转述。转述不只丢信息，还会加料。太长的走渐进式披露：
   清单常驻在上下文里，全文用 `read_user_turn` 按需取。
2. 切了必须标出来。"摘要"和"截断"是两件事，悄悄切一刀不算摘要。
3. 每段都标来源。【用户原话】是事实，【任务】是要求。平台拦不住主 agent 加料，但至少要让
   下游知道每句话是谁说的。

## 哪些判断归程序，哪些归模型

判据：违反之后会导致状态不一致的，是硬判断，程序强制；只是"效果差一点"的，是软判断，
交给模型。

运行期由平台主动发起的 LLM 调用只剩一处，就是主 agent 试答。它的输入缺一不可——少一样，
模型就只能凭空猜。其余软判断都发生在两个 agent 自己的循环里。

最要紧的几条，全在代码里：产物必须真实存在，而且是这次新写的；状态字段由代码写；三态穷举
分派，没有第四种；待答不丢，无条件透传；产物 ID 由一个只增不减的计数器发，用列表长度加一
在并行时会撞号；路径只从 `app_root()` 算。

## 主 agent 的决策点与事实通道

它做对的依据不是"懂我们的架构"，而是**在每个决策时刻手里有做决定需要的那条事实**。所以
想给它"多讲点调度逻辑"之前，先过这张表：缺的通常是某个**时刻**，不是一份架构说明；要加常驻
的话，每句都得答上两问 —— ① 没有它，它会做错哪个**具体动作**？② 这句它在哪个**时刻**才
需要（只在一刻需要的，做成注入，不做常驻）。

事实从四条通道到它手里：**常驻**（机制提示词、档位补句、技能目录）、**工具描述**、
**时点注入**（台账、回执、拒绝回执、待答透传、宿主的重建提示）、**工具返回值**。

| # | 时刻 | 要决定什么 | 此刻手里有什么 | 缺了会怎样 | 结论 |
|---|---|---|---|---|---|
| M1 | 首见需求（新会话 / 重建后） | 自己答 / 委派 / 先问 | 常驻提示词＋技能目录＋工具描述（重建后另有重建提示） | —— | 实测对 |
| M2 | 委派前 | `task` 写什么、传哪些产物 ID | "传 ID 不转述"＋`list_artifacts` | 复述正文，撑爆自己的上下文 | 实测对 |
| M3 | 委派被拒（技能 / 产物 ID 不存在） | 换名字或换 ID | 拒绝回执（含"现在有什么"清单） | 卡住或瞎猜 | 机制在，未实测 |
| M4 | 同轮收到"完成"回执 | 够不够 / 接着派谁 / 怎么交代 | 回执（交付行、产物清单含**位置**、【下一步】） | 漏路径、瞎复述 | 实测对 |
| M5 | 同轮收到"它在要信息"回执 | 只说明"委派了什么"，**不许复述问题** | 回执（含问题原话）＋机制提示词那条 🔴 | 用户看到同一个问题两遍 | 实测对（模型正文里没有问题句） |
| M6 | **投回跑完那一拍** | 接着干什么 / 是否重派 | **补录回执（`platform.feed`）**＋台账 | 照旧回执重派同技能（实测过：多跑两趟、卡片重复） | 已修，实测对 |
| M6b | 投回后仍缺信息 | 同 M5 | 补录回执（kind=waiting，带问题原话）＋台账 | 同 M5 | 与 M5 同源，未实测 |
| M6c | 投回后失败 / 平台故障 | 重派还是换法 | 补录回执（故障段＋【下一步】三档处置） | 说假话 / 乱重派 | 未实测 |
| M7 | 自己 `ask_user` 之后 | 把答复对上问题 | 工具返回"已提交"＋答复即下一条消息＋提示词那条判据 | 对不上问题、重复问 | 实测里技能文本与机制冲突的走法已拍 |
| M8 | 多技能顺序 / 依赖 | 先派谁、依赖怎么给 | 机制提示词（传 ID）＋台账 | 顺序错、丢依赖 | 实测对 |
| M9 | 用户中断之后 | 上一轮到底发生了什么 | 有已落库的部分正文；**没有"这轮被中断"的标记** | 误判上一轮完成 | 未证，先记 |
| M10 | 待答期间又想重派同技能 | —— | 台账＋机制提示词 | 多一条任务、重复劳动 | **结构已兜**：`_supersede_old` 不碰 waiting，答复不会丢 |
| M11 | 会话重建后第一拍 | 要不要看历史 | 宿主的重建提示（"有历史、按需读"） | 当新会话答 | 实测对 |
| M12 | 已建图、技能更新过 | 手里技能是不是新的 | **无事实** | 可能因"怕版本旧"重派 | 未证，先记 |
| M13 | 执行器内部写失败 | 需要知道吗 | 不需要——执行器自己兜底，结果在回执里 | —— | 不补 |
| M14 | 用户答了一张已作废的卡片 | 这条消息算什么 | 重建提示（若有）＋台账 | 迷茫、乱派 | 未证，先记 |

未证的三个（M9 / M12 / M14）先记在 `evolution.md` 的欠账里，没证到"它会因此做错"之前不补。

## 可观测性

`trace` 是事件总线。记录器和展示层各自渲染事件，谁也不去读对方渲染出来的东西。
"不许把渲染出来的文本反解析回结构"是全局判据，改这块之前先过一遍。

**日志只记标识与字数，不记正文**（见 `principles.md`）：消息正文默认只记开头与字数
（`trace.render_message` 的 `_content_for_log`），全文要看置 `SXAGENT_LOG_PROMPT=1`；
CLI 的轮次记录（`app/runtime.py:_render_tool`）对三个读工具早就只记"读了啥、多少字、
原文在哪"——两处同一口径。

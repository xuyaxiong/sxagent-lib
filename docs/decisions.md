# 关键决策（为什么这么设计）

这份文档回答"当初为什么这么定"。只记现行有效的结论，被推翻的不留。

## 五条设计原则

这五条互相咬着，改一条，另外几条会跟着变。

理解要柔性，状态要硬。平台不抽参数、不猜模型想要什么，用户原话原样往下传；但状态由代码写，
分支穷举，不允许"大概是这样"。柔的地方不设防，硬的地方不留缝。

能靠既有事实判定的，不发明协议。产物落盘就是完成，不需要一个 `finish` 工具来声明；要信息
就由执行器申报，不需要一个 `status` 枚举来描述。多一层协议，就多一处会撒谎的地方。

能靠代码算的，不交给 LLM；能靠 schema 约束的，不靠提示词。决策走
`with_structured_output`；三态干脆不是 LLM 决策，由结构定。

平台少约束 skill 作者。形式能跑就行，效果由作者迭代。任何依赖作者配合的机制都是脆的——
作者不知道有这个约定，机制就悄悄失效了。

交接靠硬机制，软判断收到最紧。委托负载由平台硬拼；要信息由执行器自己申报；平台发起的
LLM 调用只剩试答一处。

## 砍掉的（曾经以为必需）

| 砍掉 | 为什么 |
|---|---|
| `finish` 工具 | 产物落盘就是完成。用工具参数传决策，模型不调，决策就丢了 |
| `status` 枚举 / `deliverables` 清单 / `criteria` | 平台约定只有一句"交付物调 `write_artifact`"，"产物在不在"这个既有事实就够了 |
| 判定那次 LLM 调用 | "完成没"归主 agent、"在不在要信息"归执行器申报。两个语义拆开，根因就没了 |
| `interrupt` 模式 | 它要解决的问题已用别的方式解决，见下一节 |
| 草稿 / 断点外置 | 接受重跑，换掉一整类 bug |
| 参数声明（`Skill.params`） | 逼作者声明就是约束作者；实测模型还会改写参数名、算错并集，硬路径换不来可靠性 |

## 几条最贵的教训（全是实测换来的）

一、模型的话是线索，不是事实。它声称完成、自报交付清单、被提示词约束参数名，这三处都不能
当事实用。推论：模型的产出要参与逻辑判断的地方，要么用代码验证它，要么别用它。

二、平台只保证产物。正文交付不保证，也不为它造机制。四家参考实现没有一家支持"交付物在
正文里"，交付物一律走独立通道。

三、别断言模型走了几步。LLM 是概率的，数量断言必然脆。有效性靠平台造路：校验、枚举、拒绝、
按需取，不靠措辞。

四、不要用正则去检查判断。判断的反面是开放集合，正则只能枚举当时想到的那几种写法，想不到
的不报错，只是静默漏过。所以先分两件事：能算出确定答案的（两版语法树是否相同、字符串有没有
变、键集合、文件在不在），可以写成脚本，报红也没关系；只能靠读才知道好不好的（说清了吗、
该不该写、这算不算讲历史），一个脚本都不要造。

后者是故意不造，不是还没造。这类检查越全绿，越说明它守的是自己。文本体例只有判据和人的
眼睛。

## 为什么不走 `interrupt()`（最容易被误读的一条）

先说清楚：interrupt 本身没问题，实测跑得通，主上下文还更小。不用的原因是它要解决的两个问题
这里已经用别的方式解决了。"提问走向不确定"，是因为执行器从不直接问用户，没有"答给谁"的
歧义；"挂起恢复"，是因为 `Task.stage` 由代码写，恢复是纯代码查表，LLM 不参与。

若将来确实要做 HITL，把提问做成图节点而不是工具。节点里调 `interrupt()` 不产生
`tool_call`，"悬空 ToolMessage → 上游 400"这个问题就从根上消失了。

## 设计依据（不是独创）

两个参考实现。DeepAgents 给了 subagent 的 `task` 工具、skills 的渐进式加载、子 agent
ephemeral/stateless 这三个做法；Claude Code Skills 给了 `SKILL.md` 的渐进式披露和子 agent
的上下文隔离——子 agent 不能反问用户。

决定性的一点是，这两家的子 agent 都是纯函数：跑一次、出一份报告、不留状态。所以"重复问
用户""状态间歇丢失""提问写进正文"在它们那里压根不会发生。本库真正新的东西很少，主要是把
这些验证过的结构搬到需要跨轮交互的场景上，并补上 `Task` 这一层状态载体。

## 图的形状：四个节点，几条硬约束

投递和台账拆成两个节点。投递这一步里同步跑执行器，要 60 到 120 秒，节点名如果只叫
"准备"，会把最重的那件事藏起来。拆开之后 `feed → prepare` 的先后由图的边保证，不需要靠注释提醒。

待答一次只摆一个。CLI 摆出来是哪条，用户答的就是哪条，归属由通道决定。`skill` 参数只在跑批
的时候用来点名。

渲染只有一条路。`render_relay` 只管每条待答怎么排；段名、缩进、顺序都交给
`handoff.render_hop`，词汇表只有一份，避免两边各写一套。

跑主 agent 用 `stream`，不用 `invoke`。`invoke` 会把整个循环跑完才返回，中间"模型调工具、
工具回模型"的全过程都是静默的，界面上看不到任何东西。

执行器用属性访问（`executor.run_task`），不用 from-import。晚绑定，这样装配和测试的时候
替换实现才生效。

`finalize` 里那条注入留着。撤掉它对主 agent 复述问题没有效果，真正治住它的是
`agent._StopWhenPending`：问题出在"它有机会说"，不在"它看得见"。

## 接宿主时的选型：显示走事件订阅，别按 `values` 流推 state

`node_feed` 里要跑 60 到 120 秒的执行器，而 `stream_mode="values"` 是每个 super-step 才输出
一次，那段时间一个 chunk 都不会输出。所以宿主如果想在界面上看到进度，应该订阅事件，不要去推
state。这是接宿主时的一条选型提醒，不是性能缺陷。

真要按 `values` 推也不是不行，但投递得改成异步任务，图要重新长出条件边。CLI 已经在走事件
订阅了，事件在节点内部就发出来，所以那段时间界面不黑屏，宿主照着做就可以。

## 注入：技能来源与产物库

库要能顶掉现场产品（`sx-agent`）那套 harness：它的技能在 OSS 和数据库里，产物也落 OSS，
本地 CLI 则是磁盘文件夹加文件系统。所以这两处收成接口，库自己的代码只认接口，宿主注入实现：

- 模型：langchain 的 `BaseChatModel` 实例。主 agent、执行器、试答三处共用同一个；不给就用
  `config.get_model()`（读 `.env`，单机自用那份）
- `skills.SkillSource`：`get` / `values` / `files` / `read_file`，磁盘实现在 `skill_pack.py`
- `artifacts.ArtifactStore`：`put` / `get` / `has` / `items` / `where` / `clear`，内存在
  `artifacts.py`

渲染留在库里（`render_catalog` / `skill_file_prompt` / `artifact_index_lines`），实现只过数据：
措辞一旦分叉到实现里，换一个后端就换一套话，提示词里那些判据跟着失效。`where()` 给裸值
（本地路径或 URL），"位置：…" 那个标签由库拼。

接口各自的不变量写进 Protocol 的 docstring，那是实现方唯一的对照物：`read_file` 只认
`files()` 报过的路径（路径穿越、二进制、超大文件全靠这一条挡），`put` 返回那一刻东西就得在。

产物库还多两条，都是"IO 挡在哪、号从哪续"上的：

- **`put` 异步、读同步**。宿主落 OSS / 数据库是网络 IO，同步接口会把它逼进"阻塞事件循环"
  或"自己攒一个写队列"两条烂路；读反过来 —— 库的语义本来就是"读必须廉价"（宿主自己缓存 /
  预载），廉价的东西不该逼调用方 await。
- **ID 是随机短号**（`art_` + 8 位十六进制，`_next_aid`），发之前问一次 `has()`。试过自增
  序号：序号得知道"这段对话已经发到几了"，而会话对象是每请求一个（`with session()`）——
  挂会话上就跨轮重来；想从产物库续号，又得把发出去的 `art_007` 解析回数字（渲染出去的
  东西再解析回结构：格式改一处、解析忘一处，就静默发重号）。随机号不挂任何状态，跨轮、
  跨重启都不会重；代价是号长一点，抄错会当场报错（"没有这一条"），不是静默错。

模型这一处还带出一条：`config.py` 原来在 import 那一刻就 `load_dotenv()`，宿主只要 import 这个
库，进程环境就被动过。现在挪进 `load_env()`，第一次真要用到配置时才读 —— 注入了模型的宿主全程
不碰 `.env`。日志目录同理，原来 import 就 `mkdir`：现在挪到第一次写日志那一刻（`recorder._fh`）。

日志目录没有做成 `build(log_dir=…)`，走的是 `recorder.use_dir()`。理由是结构事实：日志文件按
**会话**开（一个 `session()` 一个文件），而 `build()` 一次装配服务所有会话 —— 同进程两个图时，
后 build 的那个会把目录改给所有人。`artifacts.use_dir()` 是同一个形状，两个目录一个规矩。

公共面收在 `sxagent/__init__.py`：装配（`build` / `next_pending` / `asked_text`）、配料
（`Skill` / `SkillSource` / `LocalSkills` / `DEFAULT_SOURCE` / `builtin_skills` /
`ArtifactStore` / `MemoryArtifacts` / `DEFAULT_STORE`）、接线（`session` / `trace` / 那几个词汇
类型）。`agent` / `executor` / `handoff` / `stream` / `recorder` / `llm` / `aio` / `config`
不出：它们是内部结构，公共面变了才算破坏兼容。守卫盯着"`__init__` 里 import 的名字都进
`__all__`、`__all__` 里没有死名字"。

技能这一处顺带删掉了三个换表口子（`registry.testing`）和那个模块本身（`registry.py`）。口子
存在的理由是"全进程一张当前表"，而注入之后"换一批技能"就是换一个来源实例——构造比改全局
直白，也不会再漏清另一个全局（`PACK_DIRS` 就漏过一次）。表回到 `skills.py` 里当字面量，
读走 `builtin_skills()`：这一步之后没有任何东西在运行时改它，模块留着只会让名字骗人。

这一层最容易破的地方是"收下了参数、却没往下传"：`build(skills=…)` 收下的来源曾没传到投递那条
路（用户答复后的重跑），而它不报错。所以注入要断在**每条路**上，比身份（`is`）而不是比行为——传默认值进去
等于没验。

## 模块怎么切

有几个模块是拆出来的。拆不是为了整齐，是合在一起会长出具体的病。

技能表曾经单独住一个模块（`registry.py`），是因为它原来定义在 `skills.py`、被三处各绑了一份。
由此长出两个病：`read_skill` 为了读到"替换过的那份表"得反过来 import 编排层；换一次技能要赋
两处值，漏一处，多轮投递时执行器就像换了个人。把表收进一个模块，纪律换成了机制。

那个模块后来撤了（见上一节）："换一批技能"归注入之后，它剩的只是一个字面量加一个取副本的
函数，表就搬回了 `skills.py`。当初治的病不会再犯——读的人走 `builtin_skills()`，拿到的永远是
副本，没有第二个绑定点。

`recorder.py` 从 `trace.py` 拆出来，是因为它是视图：记录器要认识 `handoff.decision` 才能渲染
决策块，而总线不该认识领域词汇。留在总线里，基础能力就传递依赖了领域层，`handoff` 永远抽不
出去。

`session.py` 存在的理由是多个会话共用一个进程。状态挂模块级是"一个进程一个会话"的形状，包成
库去接多用户 web 时，用户 B 会看到用户 A 的全部产物。内部传播用 contextvar 而不是一路传参：
传参要改上百个调用点、每个业务函数多一个参数，等于污染分层；contextvar 在 async web 里天然
对齐，每个请求一个 context。

`aio.py` 和 `llm.py` 是两个小入口。前者保证一个进程一个事件循环（`asyncio.run()` 跑完就关
循环，而缓存的 httpx 客户端绑在创建它的循环上）；后者让 `agent` 和 `executor` 不必互相 import。

## 注释为什么这么少

早先代码里住着两类东西。一类是论证，写"为什么不那么做"，篇幅比代码本身还长；一类是复盘，
写"原来怎样、实测几次、出过什么事故"。

论证一直在变，写下来就成了第二份实现说明，改了代码还得记得回来改它，忘了就变成假话。
复盘是过程记录，git log 已经存着，而且更准。两样东西混在注释里，读的人要先分清哪句是规矩、
哪句是故事，分完还得去 `docs/` 里拼另一半。

清完之后只留三种：调用方必须知道的接口，碰了会坏的不变量，改了会出事的坑。其余按内容归位，
六类各一个家，位置写在 `CLAUDE.md` 第四节。所以代码里看不到"原来是这样"，也看不到日期和
"沿革"——那些要么在 git 里，要么在本文档里。

## 工作方式

做设计时的几条做法，下一轮迭代同样适用。

先批判性看业界怎么做，再决定要不要自造。讨论先行，把"验什么、怎么验、预期是什么"说清楚，
再动代码。结论必须实测，"想当然"的想法几乎全被推翻过。分支必须闭合，凡是靠约定排除掉的
组合，都该改用枚举。

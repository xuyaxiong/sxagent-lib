# 演化方向（接下来往哪走）

这里记已知的边界和打算做的事。顺序就是优先级建议，没有时间承诺。

## 现在离生产还差什么

| 项 | 现状 | 严重度 |
|---|---|---|
| checkpoint | 用的是 `InMemorySaver`，进程一重启或开多 worker，任务状态就没了 | **体验向，不是上线硬前提**（2026-11-18 用户定：先记录、暂不处理）——重启/发版会丢"正在生成那轮已流出的正文"与"挂起的提问"；影响大小看三件事：发版频率、是否多 worker、待答是否跨夜 |
| 产物存储 | 内存里的 dict，重启即丢 | 和 checkpoint 一起修，它们是一对 |
| 长期记忆 | 没有，`store` 和 `memory_context` 都还没做 | 导致跨会话的参数复用做不到，新会话可能被重新问一遍 |
| 执行器失败处理 | 处置权归主 agent（软判断）：平台只做故障分类 + 给机械的处置建议，重派与否由主 agent 定 | —（不是差距） |
| 并发执行器命名空间 | **已实测（2026-11-18，两场景）**：主 agent 一拍发两个 `delegate` → 两个执行器真并发（窗口重叠、总时长≈max）；工具行/产物/回执/台账归属全对；两边同时提问时卡片一次摆一张、答完下一轮接力摆出、答复定向投回不丢（未覆盖：3+ 并行、并发中一个失败） | 低（原判「完全没验证」已销） |
| 换模型 | 换模型或换端点之后，必须重新做端到端验证 | 硬约束，详见下一节 |
| 台账注入 | 全量注入（已确认）；但每轮**追加**一条，历史里会攒下过期台账 | 低：要改得连记录层一起改，见下面的欠账 |

## 建议的顺序

1. 持久化（体验向，按上面那条的判据决定时机）。checkpoint 换成 Sqlite 或 Postgres；
   库自带的产物库仍是内存的（给 CLI 用），宿主要持久化就注入自己的（现场产品已经把产物落
   DB + OSS，这条对它已成立）。
2. 长期记忆。`store` 和 `memory_context`，让跨会话能复用。
3. 错误处理。执行器没登记结果时怎么重试、怎么降级。

## 换模型这条是硬的

执行器这套模式对模型有要求。我们实测遇到过一个模型在 `response_format` 上静默失效：活干完了，
返回空消息，不报错，也不抛异常。

这是最危险的一类失败，因为症状是"系统看起来成功了"。所以上线选型、换端点、升级模型之后，
都必须重跑一遍端到端验证。

怎么验 —— `uv run python -m app.chat`，你当用户走一遍关键链路：

1. 闲聊一句 —— 主 agent 自己答，不委派。
2. 让它用 `skills/lesson-prep` 备一节课 —— 委派、执行器交付、产物落盘、主 agent 报 ID 和路径。
3. 走一遍待答 —— 话里明说"直接派活、缺什么让执行器来问我"（不说的话主 agent 会自己先问用户，
   走不到执行器）；执行器 `ask_user`、主 agent 试答、答不上登记待答、平台透传。
4. 答复它 —— 投递重跑、收工。

看的是每一跳有没有真的发生，不是回复好不好看。试答那次结构化调用是静默失效最先露头的地方：
结果在决策记录里（`can_answer`）；日志里**没有** RESPONSE 块是正常的（那一步
`log_response=False`，结果改由决策记录承载），要看的是有没有"两次都失败 → 退化到保守默认
值"。产物要真落盘，`runs/<tag>/results.json` 里的 `llm_calls` / `artifact_writes` /
`run_tasks` 对得上才算走通。

## 已知的欠账（都是小口子，记着免得忘）

- 同步文件 IO 还在事件循环里：记录器每行 write 加 flush 没有锁，`skill_pack.read_text` 和
  `artifacts.write_text` 同理。全链路异步之后它们卡的是整个循环。单会话下是微秒级，多会话
  高频流式下会不会成瓶颈没量过，要先测再定级。
- `session` 的默认会话跟进程同生共死（这是设计，已写进 `session.py`）：进程即会话的宿主、
  跑批每 case 一清、多会话宿主每会话开一个 —— 支持的三条路都不漏，串数据也有护栏兜着。
- 落在"第二步之后"的抖动，这一轮就真失败了——**接受，不做"接着跑"**（`decisions.md` 里
  "接受重跑，换掉一整类 bug"管这条：从头重跑 state 干净、副作用不干净）。复核过：11 次真会话
  里一次都没出现过；哪天出现了再拿现场数据选型。
- `TaskStage` 另有三个状态是**故意不建**的：`pending`（要计划-执行分离）、
  `waiting_for_dependency`（要异步委派——`delegate` 是同步的，依赖天然在循环里解决）、
  `cancelled`（要一个取消工具）。每个都绑着一个更大的设计，设计没做，状态就没有入口；
  做了哪个再加哪个，那时它才有路径可验。
- **台账每轮追加，历史里攒着过期台账**：`node_prepare` 每轮注入一条 `SystemMessage`，而
  `add_messages` 是只增的 —— 最新的那份是对的，旧的写的是当时的状态（"⏳ 进行中"之类）。
  **改它不便宜**：记录层的增量是按位置取的（`graph` 的 `prev_n`、`app/chat.py` 的 `seen_len`、
  `runtime.snapshot` 的 `prev_len`，全是 `msgs[prev_len:]`），从中间删消息会让那套切片错位，
  要动就得连记录层一起改成"按 id 取增量"。**用户定（2026-11-18）：先不动**（没证到痛；等实测出现"上下文被过期台账撑坏"再谈）。
- **主 agent 的决策点还有三个"没证到会做错"的格子**（全表见 `architecture.md` 的「主 agent 的
  决策点与事实通道」）：M9 用户中断之后它看不到"这轮被中断"的标记；M12 已建图会话手里是技能
  快照，它无从知道技能库已经更新；M14 用户答了一张已作废的卡片（重建 / 换图之后）。三个都
  等实测里真出现误判再谈补法——**别用机制去兜没证到的问题**。
- **试答会答错，平台验不出**（2026-11-17 实测，两技能冒烟）：试答（`_ask_main`）是自己判断
  "我上下文里有没有这条信息"，判错了平台没有结构手段发现。现场：执行器问「学生基础和常见卡点？」，
  试答把手里的**上一个答复**（"探究发现型，侧重小组合作探究"）原样塞了过去——答非所问，执行器
  拿着错误前提继续。代价是一轮无谓问答（执行器有"答复没答到点上就再问一次"的规则，能自愈）。
  **修法候选：把试答从"生成"改成"搬运"**——只能回"哪条消息的哪段原文"，平台校验那段原文确实是
  那条消息的子串（结构判据），验不过就判"答不上"、弹卡片。先记账，不动。
- **投回后"仍缺信息"已实测（2026-11-18）**：答非所问 → 照投 → 重放仍缺 → 补录回执（kind=waiting、带问题原话）+ 台账翻回「它在要信息」+ 新卡片重问；正式答复后投回、交付、收尾全对。**投回后"失败"用户定（2026-11-18，丙）：等自然出现**（渲染与 delegate 那条路共用、单测已覆盖；真故障是环境问题）。
- `_user_turns.after` 只带**紧邻的那一条 AI 消息**：问题不在紧邻位置时（AI 问 → 用户说别的 →
  AI 答 → 用户回答最初那个问题），它指的就不是问题。**判定条件**：执行器读到原话后仍然问
  "这句在回答哪句"，就算不够用——真出现再谈加宽，索引不该为假想的情况涨。

## 观察项：主 agent 会自干技能流程

实测（2026-11-18）：即使机制提示词写着"这类活默认委派"，主 agent 在"工具在手、材料在手边"时仍会
自己把整趟技能流程干完（exam-grading 那趟：`read_skill` → 读参考文件 → 识图 → 交付 json，产物正确）。
**口径：谁做都行、按 SOP 就行（用户定，2026-11-18）**；代价是自干会把技能原文、参考文件与工具结果
留在主 agent 的上下文里，长会话连干几个技能会变慢变贵。**不采取任何"收窄能力"的处置** ——
主 agent 与 subagent 是对等执行器（用户定的原则），打破对等要用户拍板；真出现上下文膨胀的会话，
对症方向是主 agent 的历史压缩，不是禁止自干。

## 工具重试将来上收到库（有顺序依赖，先记在这）

现在工具的重试活在宿主那边：重试循环写在工具函数内部，"刚失败过就不再放大重试"的记忆也在宿主侧。
方向是上收到库的工具调用策略层——重试 ＋ 近期失败窗口，宿主只声明策略（哪些异常可重试、
次数、窗口），新工具接进来只用声明，不再各自复制重试写法。

上收现在做不了，卡在一条依赖链上，两步都是硬前置：

1. 库要接管重试，宿主工具就得先不再自己重试（否则双重重试）；而工具的重试现在同时服务
   旧 harness 和本库两条执行路径，旧的那条退役之前拆不得。
2. 库从外面重试，前提是"工具失败了"对库可见：现在宿主的工具把失败吞成字符串**返回**，
   在库看来是一次成功调用。得先把失败翻成结构（抛出来 / 错误状态的消息），这会动到全部
   服务工具——所以它该等一个自己的理由（审计、指标要用失败事实），不该被重试这一个机制
   拖着做。

过渡期由宿主侧的近期失败窗口兜着：不拦调用，只压"烧光一次之后还照着原来的次数重烧"。

## 公共 API：承诺整张图

目标是**取代**现场产品（`sx-agent`）那套 harness。判据：宿主什么都不缺，就缺本库独有那一段
（执行器 + Task 跨轮状态 + 交接），而它的图、状态、存储都长成了自己的样子——所以承诺整张图，
模型 / 技能源 / 产物库 / checkpoint / 工具集 / 目录由宿主注入。

接口清单与 `build(...)` 的签名，动工前摆出来过一遍再写。

注入点这一批做完了：模型（`BaseChatModel` 实例，主 agent / 执行器 / 试答三处共用）、产物库
（`ArtifactStore`）、技能来源（`SkillSource`）、checkpointer 与长期记忆的口子、宿主的领域工具
（`tools=`）、宿主的业务提示词（`system_prompt=`，追加在机制段之后，机制段不可替换）、
日志目录（`recorder.use_dir`）。公共面收在 `sxagent/__init__.py` 的 `__all__` 里，
有守卫盯着"导进来的名字都表过态"。

配套的一条：import 这个包不在宿主那边留东西 —— 不读 `.env`，也不在磁盘上建目录。

# 演化方向（接下来往哪走）

> 已知边界与计划；**顺序即优先级建议**，没有时间承诺。

## 当前边界（原型 → 生产还差什么）

| 项 | 现状 | 严重度 |
|---|---|---|
| checkpointer | `InMemorySaver` —— 进程重启 / 多 worker 就丢任务状态 | 🔴 **上线前必须解决** |
| 产物存储 | 内存 dict —— 重启即丢 | 🔴 与 checkpointer 成对修 |
| 长期记忆 | 没有（`store` / `memory_context`） | 跨会话参数复用做不到：新会话可能被重新问一遍 |
| 执行器失败处理 | 只有 `failed` 终态，**没有重试 / 降级策略** | 中 |
| 并发执行器命名空间 | **完全未验证**（节点内调用 → 命名空间按调用顺序分配） | 中（结构性） |
| 换模型 | 换模型 / 端点后必须重新端到端验证 | 硬约束（见下） |

## 演化方向（建议顺序）

1. **持久化**：checkpointer 换 Sqlite/Postgres ＋ 产物库换真存储 —— "重启不丢"的前提，它俩是一对
2. **长期记忆**：`store` / `memory_context` —— 跨会话复用
3. **公共 API 稳定化**：`__init__` 导出面 ＋ 配置注入（库收显式配置，不隐式读 `.env`）
4. **测试体系**：pytest 套件（当前仓库还没有测试；重建时把守卫断言逐条迁入）
5. **错误处理**：执行器不登记结果时的重试 / 降级

## 换模型的硬约束

执行器模式对模型能力有要求。实测：某模型在 `response_format` 上**静默失效**——
干完了活、返回**空消息**、不报错、不抛异常。

> 🔴 **这是最危险的一类失败：症状是"系统看起来成功了"。**
> 上线选型 / 换端点 / 升级模型后，**必须重跑一遍端到端验证**。

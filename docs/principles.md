# 行为原则

> 两个前身项目里反复踩出来、最后定成规矩的东西。每一条背后都有一次真实的返工，
> 所以这里留了"当时怎么发现的"—— 把那段删掉，剩下的就只是一句口号。
>
> `CLAUDE.md` 里是同一批的一句话版，动手前过那一遍；这里是想知道"为什么"的时候翻的。

## 工作方式

### 讨论先行

动手前说清做什么、为什么、预期是什么，等确认再写代码。要测试的，先说清验什么、怎么验、
预期是什么。

### 结论必须实测

不说"我觉得应该没问题"。而且优先真实模型 —— 假模型能跑通图逻辑，但行为差很远：
真模型会"将就着做"，也会"吹毛求疵"。

前身项目里几乎每一条"想当然"都被实测推翻过。以为"有产物就算完成"，实测发现产物是残次品
也照样算完成；以为"两个布尔值能表达三态"，实测四种组合只有三种合法，剩下那种靠约定排除。

### 批判性审视，不要照办

用户提的方案也是一家之言。先读参考实现，再决定要不要自造，不要用推理替代读源码。

前身项目里，参考实现就在本地，却在没读的情况下自造了一整套方案；读完才发现其中一半是
过度设计。

### 缺信息就搜或问，不要假设

不清楚库的行为、模块的实现、配置的内容、外部服务的返回格式时，先搜一遍或直接问用户。
不要凭经验补一个看起来合理的答案 —— 猜出来的东西不会说自己是在猜。

### 不迎合

AI 是协作者，不是执行工具。用户要求跳过类型注解、跳过测试，或者方案本身有明显缺陷
（选型不当、漏了边界条件、异常没处理）时，直接指出并给替代方案，不要只说"好的"。

一味迎合不是帮助，是失职。

## 设计

### 分支必须闭合

每设计一组分支，问三件事：闭合吗（覆盖所有可能吗）？互斥吗（有没有一种情况同时落进两个）？
每个都被妥善处理了吗（有没有"落进 else 但 else 什么也没做"的）？

用几个布尔值表达多种状态、"靠约定才能排除"的组合，都是不闭合的信号，该换成枚举。

### 别自己造机制

想加一层机制之前先问两句：参考实现里有吗？它是在给"大家都支持的形态"打补丁，
还是在给"没人支持的形态"打补丁？

前身项目里，一个真实技能把交付物写在回复正文里，据此提了四条机制，全被否 ——
读完四个参考项目才发现，没有一家支持"交付物在正文里"这个形态。

"我发现一个可能的问题 → 提议加一层机制"这个反射要按住。没证到的问题别用机制去兜。

### 交接三问

每一处交接都要过这三关：

1. **交接了什么** —— 这一跳该给的东西给全了吗？顺着信息流走一遍：产出它的环节 →
   需要它的环节，中间断了吗？
2. **有没有被截** —— 有 `[:N]` 把话切了吗？切了标了吗？不标是最糟的一种：
   读的人分不清"它就说这么多"还是"被切了"，而这两种情况该做的决定完全不同。
3. **长了怎么办** —— 走渐进式披露（清单常驻、正文按需取），还是显式截断？没有第三条。

"摘要"和"截断"是两回事：要短就该另写一段短的话，而不是把原话切一刀。

### 信息给全，决策结构化

喂给模型的东西少一样，它就凭空猜。前身项目里踩过四次，每次都是同一个形状：判定提示词没带
技能指令、没带给定条件、失败分支没带缺什么、答复没带上它回答的那个"问"。

一条信息脱离了它的语境就不是信息 —— 代词、选项字母、省略句都是这样。
平台不判断"这句是不是短应答"（那是语义判断），而是结构上保证成对：收下答复的那一刻，
把它回答的那句一起原样截下来。

决策的结果要结构化（走 structured output），不要用工具参数传决策 —— 模型不调，决策就丢了。

### 断言要断机制，不要断模型走了几步

模型是概率的，数量断言必然脆。稳的断言断的是：平台机制（代码，确定性）、产物性质、
不变量、目标状态。不要断"走了几步""输出多长"。

而且别指望模型去走你想验证的那条路 —— 让平台把路造出来（故障注入、构造初始状态），
不然那条路压根没被走到，两条臂会逐字相同地都挂同一条。

### 不要用正则处理语义

语义是开放集合，正则只能枚举已知的，枚举不到的静默漏过 —— 于是守卫给人一个"有人管着"的
错觉，实际只覆盖了你想得到的那几种。

造守卫前先分清这条判据是什么：机械的（键集合、AST、文件在不在、词表命中）可以进守卫；
语义的（说清了吗、措辞对不对、有没有歧义）不能，如实说这里没有机制，靠周期性审。
为了让正则够到语义而放宽它，是正在犯错的信号。假红比不守更坏。

### 过期结论不留

被推翻的结论直接删掉，不要留在文档里 —— 留着会造成干扰：读者从文档中间进去会被带偏，
而且不知道自己看的是过期的。要留就留在 git log 里：那里天然带着时间，也天然只被想追的人翻到。

（说清"当初为什么这么选"是另一回事，那是现行结论的依据，`decisions.md` 记的就是它。）

### 场景沉淀成回归集

用户口述的场景当场记下来，写清输入、期望、为什么重要、当前状态。架构迭代最容易
"修好一个、弄坏一个" —— 前身项目里去掉一个工具修好了"主 agent 能自己干活"，
却立刻暴露出隔离失效和重复委派。

每次改动后回来跑一遍，更新状态表。要标出"未验证"和"不达标"，不要只记通过的。

### 平台少约束作者

任何依赖作者配合的机制都是脆的 —— 作者一句自然语言就能覆盖平台约定。
所以平台机制要建立在既有事实（产物落盘没有）上，不要建立在执行器的声称上。

## 文本

### 用词职业化

文档、注释、docstring 都用领域内的词，不自造说法：报错叫报错（抛异常、失败），模型的产出叫
输出（生成、返回），不叫"炸""吐"。想不到现成说法就去查别人怎么写，查不到再自己起名 ——
起的名当场说清它是什么，别默认读者已经会了。

口语词和自造词都让读者先翻译一遍才接得住，而翻译是各人各译的：同一个"炸"，有人读成抛异常、
有人读成整轮失败。词不统一，读的人就得回去翻代码确认。

### 报错信息要清晰准确

说清哪里不对、合法值是什么、去哪儿看。含糊的报错比不报更费时间 —— 读的人得先猜它说的是
哪一层，猜完还得自己去翻代码。
